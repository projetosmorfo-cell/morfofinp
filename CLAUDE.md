# MorfoFinP (MFinp)

App de controle financeiro pessoal do Rafael. Primeiro produto publicado da Morfo — sem site guarda-chuva (`morfo.app`) ainda, então este repositório é hoje o produto inteiro.

Contexto de produto (decisões, modelo de dados, roteiro de publicação) fica em `docs/`. Este arquivo é o resumo prático pra trabalhar no código.

## Stack

- **Vite + React + TypeScript** — SPA pura, sem backend/servidor.
- **Dexie.js sobre IndexedDB** — todo o dado é local, no aparelho da pessoa. Sem banco externo, sem Firebase. Ver `src/db.ts` pro schema.
- **Sem router** — nada de `react-router-dom`. Navegação entre telas é só estado do React (`useState` em `App.tsx`), de propósito: qualquer lib baseada em `window.location`/`history`/`new URL(...)` quebra ao abrir o build direto como arquivo (`file://`), porque `window.origin` vira a string inválida `"null"` nesse protocolo. *(Removido em 30/08/2026, depois que `BrowserRouter` — que já tinha substituído `HashRouter` no mesmo dia — ainda quebrava sob `file://`.)*
- **Sem PWA** — nada de `vite-plugin-pwa`, manifest ou service worker. *(Removido em 30/08/2026 — decisão do Rafael de não seguir no modelo PWA/instalável-via-navegador.)*
- **Hospedagem (quando publicado): Cloudflare.** *(Mudou de Netlify em 30/08/2026.)*

## Como rodar

O fluxo de trabalho padrão do Rafael, enquanto o app está em fase de MVP, é o build local navegável — um único `index.html` com tudo inline (JS+CSS), aberto direto com duplo clique (`file://`), sem servidor:

```
npx vite build --config vite.config.local.ts   # gera dist-local/index.html
```

Isso funciona por design: como não há router nenhum (ver seção Stack acima), não existe navegação baseada em URL pra quebrar sob `file://`. Esse é o formato que é entregue a cada iteração — **nada é publicado (hospedagem, Artifact, etc.) até o Rafael decidir explicitamente publicar uma versão.**

Também dá pra rodar com hot reload de desenvolvimento, via HTTP:

```
npm install
npm run dev       # servidor local com hot reload
npm run build     # build de produção "normal" em dist/, para quando for hospedar de verdade
```

## ATENÇÃO — comando correto pra checar tipos (correção crítica, 01/09/2026)

**O comando `npx tsc --noEmit`, usado em TODA rodada anterior deste projeto como prova de "tsc limpo", nunca checou coisa nenhuma.** O `tsconfig.json` da raiz tem `"files": []` e só `"references"` pra `tsconfig.app.json`/`tsconfig.node.json` — isso faz o `tsc` bare (sem `-p`) não ter nenhum arquivo pra checar, retornando "limpo" sempre, mesmo com erro de tipo real no código. Descoberto ao investigar por que um erro de runtime genuíno (`fmtBRL is not defined`, ver rodada 01/09/2026 abaixo) não tinha sido pego por "tsc limpo" na hora de entregar.

**O comando certo é:**
```
npx tsc --noEmit -p tsconfig.app.json
```

Rodar esse comando corrigido revelou 6 erros de tipo reais (alguns pré-existentes havia rodadas, nunca detectados), todos corrigidos na mesma rodada de 01/09/2026. **Todo "tsc limpo" documentado em rodadas anteriores a esta (30/08 e 31/08/2026) deve ser lido com desconfiança** — não significa que o código realmente foi checado, só que o comando errado não fez nada. Da rodada de 01/09/2026 em diante, sempre usar o comando com `-p tsconfig.app.json`.

**Regra de negócio importante:** a base pra calcular a Meta R$ de cada grupo (Fixo/Variável/Objetivos/Segurança) é **só o salário do mês** (categoria "Salário"), não a receita total — cashback, reembolso e outras entradas avulsas não expandem a meta de gasto. **Terminologia das barras (30/08/2026):** nunca usar "faltam" — é ambíguo (parece dívida, não sobra). Use "margem" pro valor que ainda cabe dentro do teto/aceitável (não é dinheiro livre de verdade) e "estourou" quando passou do teto (esse já era claro). Ver `docs/progresso.md`.

**Grupo (antes "macrocategoria"/"bloco") — rename definitivo (30/08/2026):** o Rafael pediu pra abandonar completamente o termo "bloco"/"macrocategoria" por ser confuso. O termo escolhido (a critério do Claude Code, conforme delegado) foi **"Grupo"** em todo o código, UI, comentários e neste arquivo. Schema Dexie bumpado pra v3 com migração renomeando o campo em bancos existentes. A planilha ainda usa "MacroCategoria" como cabeçalho de coluna — trocar lá é tarefa separada, ainda pendente (ver `docs/progresso.md`).

**Grupo virou cadastro de verdade, com CRUD (30/08/2026, rodada seguinte):** antes "Grupo" era só um union type fixo (`'Fixo'|'Variável'|'Objetivos'|'Segurança'`). Agora é uma tabela Dexie própria (`grupos`, ver `GrupoRegistro` em `db.ts` — schema v4) com cadastro/edição/inativação/exclusão pela tela Categorias. `Categoria.grupo`/`Meta.grupo` continuam sendo o **nome** do grupo (`string`), não um id — renomear um grupo (`Categorias.tsx`, `salvarNomeGrupo`) atualiza em cascata, numa única `db.transaction`, todas as categorias e metas que referenciam o nome antigo; simplicidade > normalização por FK aqui, já que é um cadastro pequeno e raro de editar. Grupo com categoria vinculada só pode ser inativado (some das opções de categoria nova, histórico continua íntegro); sem nenhuma categoria, pode ser excluído de verdade. Toda tela que antes tinha um array `ORDEM_GRUPO`/`GRUPOS_DE_GASTO` hardcoded (Situação, Resumo do Mês) agora itera `db.grupos` — um grupo novo que o Rafael criar aparece automaticamente em Situação, Resumo e Planejamento, sem precisar mexer em código.

**Recorrência e parcelamento a nível de LANÇAMENTO, nunca de categoria (30/08/2026):** o Rafael foi explícito — "a lógica de recorrência e parcelamento deve ser aplicada exclusivamente a nível de lançamentos (e nunca nas categorias)". Isso revogou e substituiu o mecanismo anterior (`Categoria.diaEsperado`, removido do schema na v3). O novo modelo, em `Lancamento`:
- `recorrencia?: 'fixo' | 'parcelado'` (ausente = lançamento único, o padrão).
- **Fixo** (conta recorrente sem fim definido — aluguel, assinatura): tem `periodicidade` (semanal/quinzenal/mensal/semestral) e `regraRecorrencia` (dia fixo do mês, dia útil do mês, ou dia da semana, conforme a periodicidade). Geração das ocorrências futuras é **dinâmica por ciclo** (decisão técnica do Claude Code, conforme delegado): `avancarSeriesFixasPendentes()` (`src/recorrencia.ts`), chamada uma vez no mount de `App.tsx`, avança cada série até hoje, gerando (gravando de verdade) toda ocorrência que já deveria ter acontecido e ainda não existe — com o mesmo valor da última ocorrência real. Não pré-gera indefinidamente porque não tem fim conhecido.
- **Parcelado** (compra dividida em N parcelas, fim conhecido no cadastro): é **antecipado** — todas as N parcelas são gravadas de uma vez na criação (`gerarParcelas()`), cada uma na sua data de competência (mesmo dia do mês da primeira, ajustado pra meses mais curtos), com identificador estruturado `parcelaI`/`parcelaN` (exibido como "2/5"). Mesmo conceito de "Parc. i/Parc. n/Restam" que `codigo/build_v5.py` já usa pra projetar parcelas contratadas na planilha.
- Todas as ocorrências/parcelas de uma série compartilham `serieId` (índice em `lancamentos`).
- "Sobra real este mês" (tela Situação) foi reconstruída em cima disso: acha a última ocorrência de cada série fixa, calcula a próxima data esperada, e se ela cair neste mês mas ainda não tiver chegado (ainda não foi gerada pela geração dinâmica), mostra como comprometido — com o valor EXATO da última ocorrência (mais preciso que a média usada no mecanismo antigo).
- Formulário (`DetalheLancamento.tsx`): um lançamento que já pertence a uma série (`jaTemSerie`) só edita aquela ocorrência, nunca a série inteira — a recorrência em si fica travada nesse caso (mantém o modelo simples). Mas um lançamento ÚNICO pode virar fixo/parcelado também na EDIÇÃO, não só na criação (pedido do Rafael, 30/08/2026, rodada seguinte) — `podeEscolherRecorrencia = !jaTemSerie` controla isso, e as mesmas opções de recorrência aparecem em ambos os fluxos.

**Categorias recolhíveis com navegação contextual (30/08/2026):** em Resumo do Mês (linhas "Por categoria") e Situação ("Onde estourei"/"Onde ainda sobra"/"Aportes do mês") — nunca em Categorias, que é cadastro, não uma lista de totais — toda linha de categoria é clicável e expande mostrando os lançamentos que compõem aquele total (`ListaLancamentosCategoria.tsx`), cada um clicável pra abrir `DetalheLancamento`. Como o modal abre por cima da tela (nunca troca de tela, ver `TelaProps.aoAbrirLancamento`), fechar/salvar/cancelar sempre volta pro mesmo lugar com a mesma categoria ainda expandida — não precisou de nenhuma navegação por estado serializado.

**Tela Lançamentos (antes "Lançar", 30/08/2026):** deixou de ser formulário-primeiro pra virar lista-primeiro: obedece o mês selecionado (mesmas setas com o mesmo limite padrão de `Situacao`/`ResumoDoMes`), botão flutuante (+) pra incluir, clique num item sempre abre `DetalheLancamento` já em edição (funciona igual no mobile e na web). Arrastar o item pra esquerda no mobile expõe um atalho de excluir (com duplo check) — é só complementar, nunca a única forma de agir.

## Rodada seguinte (30/08/2026) — situação de pagamento, conta/cartão, Carteira, Planejamento

Depois da entrega acima, o Rafael mandou um feedback grande com 10 pontos. Dois exigiam decisão e foram perguntados diretamente a ele antes de implementar: (1) onde deveria viver a visão Planejado×Realizado×Previsto por nível — escolheu **nova tela "Planejamento"**; (2) o que vale como "planejado de receita" por categoria — escolheu **cadastrar manualmente** (`Categoria.esperadoMensal`), não inferir de lançamento recorrente. Tudo abaixo é dessa rodada.

**Layout de lista em 3 colunas fixas:** em toda lista de lançamento (Lançamentos, categoria expandida, Carteira) — data | título | valor — data e valor nunca quebram linha; só o título pode, sem invadir as colunas vizinhas. É CSS Grid puro (`.linha-lancamento { grid-template-columns: auto minmax(0,1fr) auto }`, ver `index.css`), cada linha é seu próprio grid (colunas não alinham entre linhas diferentes, mas isso não importa aqui — o que importa é nunca quebrar data/valor).

**Situação de pagamento (`Lancamento.pago`):** um único booleano opcional (`undefined` tratado como `true`, compatibilizando com todo o histórico real importado, que já estava liquidado). O rótulo (Pago/Recebido/Atrasado/A pagar/A receber) nunca é guardado como string — é sempre derivado na hora por `statusDoLancamento()` (`src/statusPagamento.ts`), comparando `pago` e `dataCompetencia` contra hoje. Mostrado como um pill clicável (`.status-pill`, cor por `CLASSE_STATUS`) em toda lista de lançamento; clicar alterna `pago` na hora (`db.lancamentos.update(id, {pago: !atual})`), e como tudo usa `useLiveQuery`, o recálculo em qualquer tela é automático. Fundo da linha muda (`FUNDO_STATUS`) pra não-pago/atrasado, fundo normal pra pago/recebido — não precisa abrir o lançamento pra saber o estado dele.

**Campo conta ("pago com"):** `DetalheLancamento.tsx` ganhou um select de conta (banco/cartão), com `contaId` já existente no schema desde o início — só faltava expor na UI. A semente (`seed.ts`) já carregava esse dado real desde a rodada anterior (`LancamentoSemente.conta: 'bradesco'|'cartao'`), então não precisou nenhuma migração de dado, só a tela pra editar/ver.

**Tela Carteira (nova):** um card por "lugar" onde o dinheiro está — cada conta real (`db.contas`, ativa) mais um card virtual "Cofrinho". Conta corrente (Bradesco) mostra o total do mês selecionado; cartão (Porto Seguro) mostra o total da fatura em aberto até agora (janela calculada a partir de `diaFechamento`: do dia seguinte ao último fechamento até hoje, não até o fim do mês — é literalmente "quanto já entrou na fatura que ainda não fechou"); Cofrinho mostra o saldo acumulado de todos os tempos (soma de tudo com natureza `Aporte` menos tudo com natureza `Gasto de cofrinho`, não é uma `Conta` de verdade, é uma soma virtual). Clicar num card abre a lista de lançamentos daquele lugar (mesmo layout 3-colunas + pill de status), filtrável por mês, com o botão de incluir já pré-preenchendo a conta certa (`contaIdSugerida`, ver `TelaProps`/`DetalheLancamento`).

**Situação e Resumo do Mês — generalização e novos números:**
- `categoriasDeGasto`/`gastoPorGrupo` deixaram de ter grupo hardcoded — agora cobrem toda categoria de natureza Consumo, de qualquer grupo (a única exceção é o card "Metas por grupo" do Resumo, que continua Consumo-only de propósito, igual a fórmula `SUMIFS` da planilha — Objetivos/Segurança aparecem lá sempre com gasto zero, e isso é intencional, não bug: o aporte deles é acompanhado à parte em "Aportes do mês"/`db.grupos`).
- Card "Por grupo" (Situação) e "Metas por grupo" (Resumo) agora iteram `db.grupos` (todos, não só Fixo/Variável) e ganharam uma linha "Total geral".
- "Onde ainda sobra" (Situação) ganhou a mesma `BarraMeta` que "Onde estourei" já tinha, em vez de só um `+valor` — mostra visualmente quanto ainda cabe, não só o número.

## Rodada seguinte (31/08/2026) — Transferência, categoria vinculada a cofrinho, fatura de cartão, Planejamento em 3 seções

Rafael mandou mais 4 pontos, desta vez mexendo em modelo de dados de verdade (não só UI). Esta é a primeira rodada desde a migração que precisou de um **bump de versão Dexie de verdade** (v4 → v5) — ver decisão técnica abaixo.

**1) Tipo de lançamento "Transferência" entre contas.** Rafael deixou explícito que aceitava tanto um lançamento único quanto dois lançamentos vinculados, desde que ficasse "muito nítido" qual dos dois — decisão do Claude Code (conforme delegado): **dois lançamentos sempre juntos**, nunca um só. Motivo: o schema de `Lancamento` é fundamentalmente de UMA conta e UM valor com sinal — forçar dois lados (origem+destino, cada um com sua categoria) dentro de um registro só exigiria reestruturar o modelo inteiro. Dois lançamentos com um `transferenciaId` compartilhado (novo campo, mesmo mecanismo de `serieId`) resolve com o schema como já é: um leg negativo na conta de origem, um leg positivo na conta de destino, os dois com a mesma categoria de sistema "Transferência entre contas" (natureza nova `'Transferência'`, criada sob demanda por `categoriasSistema.ts` na primeira vez que a funcionalidade é usada — não foi adicionada ao `seed.ts`). Editar ou excluir QUALQUER um dos dois lados sempre afeta o par inteiro (nunca deixa uma transferência "manca") — `DetalheLancamento.tsx` busca o par via `transferenciaId` antes de preencher o formulário, e mostra um aviso ("Metade de uma transferência..."). Natureza `'Transferência'` foi adicionada à mesma exclusão que `'Pagamento de fatura'` já tinha em `ResumoDoMes.tsx` (Entrou/Saiu e Vai entrar/Vai sair) — sem isso, mover dinheiro entre duas contas rastreadas infla Entrou E Saiu ao mesmo tempo (o Resultado não muda, mas os dois números ficam artificialmente maiores). Como é natureza nova sem uso histórico, essa exclusão não muda nenhum número já verificado.

**Decisão técnica que exigiu bump de schema:** `DetalheLancamento.tsx` precisa achar "a outra perna" de uma transferência via `db.lancamentos.where('transferenciaId').equals(...)`, e o Dexie exige que o campo esteja **indexado** pra aceitar `.where()` nele (erro real encontrado ao testar: `SchemaError: DexieError`) — diferente de `Categoria.contaVinculada` (ponto 2 abaixo), que nunca precisa de índice porque é sempre lido via `.filter()` em JS sobre a tabela `categorias` inteira (pequena, sempre carregada). Por isso `db.ts` ganhou `this.version(5)` adicionando `transferenciaId` aos índices de `lancamentos` — **sem `.upgrade()`**, porque é campo novo (nenhum lançamento existente tem valor pra migrar). Testado explicitamente o cenário que already mordeu o projeto uma vez (ver "Causa raiz" mais abaixo): criado um banco só com a v4 (código antigo, temporariamente revertido pra testar), semeado, depois reaberto com o código novo (v5) no MESMO perfil de navegador — o Dexie fez upgrade automático, sem apagar nada, ground truth de agosto continuou idêntico, e a transferência (que só funciona com o índice novo) passou a funcionar imediatamente. Isso é diferente de mudar `VERSAO_SEMENTE_DEMO` (que troca o NOME do banco pra forçar reseed) — aqui o banco é o mesmo, só o schema interno evolui, exatamente pra isso que existe o mecanismo de versão do Dexie.

**2) Categoria vinculada a um cofrinho (abate aporte automático).** Pedido do Rafael: pagar uma conta direto pelo Bradesco, numa categoria que ele já sabe ser "do cofrinho", sem precisar sacar → transferir → pagar manualmente. Novo campo `Categoria.contaVinculada?: number` (aponta pra uma `Conta`, tipicamente tipo `cofre`) — exposto em Categorias.tsx só pras naturezas onde faz sentido (`Gasto de cofrinho` e `Aporte`, constante `NATUREZAS_VINCULAVEIS`). Em `Carteira.tsx`, o saldo de uma conta tipo `cofre` (tanto no card quanto no drill-in) passou a somar não só os lançamentos com `contaId` igual ao dela, mas também todo lançamento pago de OUTRA conta cuja categoria está vinculada a ela (`categoriasVinculadasDe`) — o item aparece na lista do cofrinho com uma tag "· via Bradesco" (ou qualquer que seja a conta real) pra ficar claro que o dinheiro não passou fisicamente por ali. Testado: categoria "Gasto Cofrinho Teste" (natureza Gasto de cofrinho, vinculada a um cofrinho cadastrado) lançada com `contaId` = Bradesco — o total do cofrinho caiu automaticamente, sem nenhuma transferência.

**3) Cartão de crédito — ciclo de fatura, totalizador, pagamento neutro.** `Conta.diaVencimento` já existia no schema (e até já vinha semeado — Porto Seguro sempre teve `diaVencimento: 15`), só não tinha UI — agora exposto em `Contas.tsx` ao lado de `diaFechamento`. `Carteira.tsx` generalizou o cálculo de janela de fatura: `janelaFatura(diaFechamento, mesISO)` calcula a janela FECHADA (fechamento a fechamento) de qualquer ciclo, reaproveitando o `mes` já compartilhado do `SeletorMes` — dentro do drill-in de um cartão, "trocar de mês" passou a significar "trocar de fatura", sem nenhum componente de navegação novo (a função antiga, renomeada `janelaFaturaEmAberto`, continua existindo à parte só pro card resumido "fatura até o momento", onde o fim é sempre hoje, nunca um fechamento cheio). O cabeçalho do drill-in mostra o período exato ("Fatura de 10/07 a 09/08 · vence dia 15").

Todo `DetalheConta` (corrente, cofre OU cartão) ganhou um totalizador de rodapé (`.total-geral`) com saldo inicial do período (saldo da conta + todo lançamento anterior à janela), entradas, saídas e saldo final — pedido explícito do Rafael pra "todas as telas de detalhamento de carteiras". No cartão, uma linha extra evidencia o "Total desta fatura" (saídas − entradas só do ciclo, sem misturar com o saldo acumulado). **Nuance documentada, não bug:** o "saldo inicial/final" acumulado de um CARTÃO fica bem negativo (ex.: -R$42 mil em agosto/2026) porque o modelo nunca credita o cartão quando a fatura é paga — o pagamento é sempre um lançamento na conta que PAGA (Bradesco), nunca na conta do próprio cartão (é assim que `seed.ts` sempre gravou "Pagamento de fatura", e continua sendo assim pro pagamento novo, ver abaixo) — pra cartão, o número que realmente importa é "Total desta fatura", não o saldo acumulado, mas os dois são mostrados porque o pedido foi "em todas as telas de detalhamento", sem exceção.

Ação nova "Pagar esta fatura" (só aparece no drill-in de um cartão, quando há algo não pago no ciclo exibido): escolhe a conta de origem do pagamento (sugere `conta.contaPagamentoPadraoId`, já existia no schema — Porto Seguro → Bradesco, já semeado), cria UM lançamento na conta de origem com a categoria "Pagamento de fatura" (mesma já semeada, reaproveitada via `categoriasSistema.ts`, `pago: true`, valor negativo) e marca **todos** os lançamentos do ciclo exibido como `pago: true` + `faturaId` apontando pro novo lançamento (`Lancamento.faturaId` já existia no schema desde o início, nunca usado até agora). Neutro no fluxo de caixa (mesma exclusão de `'Pagamento de fatura'` que já existia) — a despesa não é contada de novo, ela já entrou no cálculo quando a compra foi feita.

**4) Planejamento — 3 seções coloridas + cabeçalho de grupo com 1 barra só.** Nível Categoria dividido em 3 seções (era 2): **com orçamento previsto** (borda azul), **sem orçamento mas com movimento** (borda âmbar, chama atenção pra gasto fora de qualquer teto cadastrado) e **sem orçamento e sem movimento** (borda cinza, **recolhida por padrão** — é a mais numerosa e menos relevante no dia a dia, com toggle por grupo pra expandir). Decisão do Claude Code sobre um caso que o pedido do Rafael não cobriu explicitamente: categoria COM orçamento previsto mas SEM movimento este mês (ex.: uma categoria de gasto pontual, ainda não usada) fica na seção 1 (com orçamento), não cai num limbo — ter orçamento cadastrado já é o sinal mais importante, com ou sem movimento. Nível Grupo: as duas barras separadas (Saídas/Entradas) no cabeçalho recolhido viraram **uma barra única** ("Total do grupo", soma dos totais de Saídas+Entradas do grupo) — o detalhamento separado já existe nos níveis internos (Categoria/Lançamento), repetir no topo só duplicava informação.

**Verificado antes de entregar:** `tsc --noEmit` limpo; ground truth de agosto batendo exatamente, ANTES e DEPOIS de todas as mudanças (Entrou +R$17.223,77 / Saiu -R$15.166,45 / Resultado +R$2.057,32); **teste de upgrade real de banco existente** (v4 → v5, ver acima) — o cenário mais parecido com o que aconteceria no aparelho do Rafael se ele já tivesse aberto uma build anterior; criar/editar (mudar valor)/excluir uma transferência, conferindo que os dois lados sempre se movem juntos; categoria vinculada abatendo o saldo do cofrinho a partir de um lançamento pago de outra conta; ciclo de fatura navegável mostrando o período certo; "Pagar esta fatura" marcando o ciclo inteiro como pago e criando o lançamento neutro certo; Planejamento com as 3 seções (cores + recolhimento) e o cabeçalho de grupo com barra única; build `file://` (`dist-local/index.html`) de ponta a ponta, zero erro de console.

## Rodada seguinte (01/09/2026, 4ª rodada do dia) — tela "Manutenção" (engrenagem), investigação real do medo de perda de dado por "limpar cache"

Rafael testou a build da rodada anterior, reportou que a Transferência "não tava funcionando", foi num navegador e limpou o cache — funcionou, mas aí não tinha registro nenhum (base zerada) e ficou sem condições de reproduzir/testar do zero. **Investigação técnica antes de sair implementando (evitar repetir o erro documentado no topo deste arquivo, de corrigir sintoma sem achar causa real):** medi, ao vivo via Playwright, o que de fato existe sob `file://` (o jeito que o Rafael sempre abre o app) — `navigator.serviceWorker.getRegistrations()` sempre lança erro sob esse protocolo (`The URL protocol of the current origin ('null') is not supported` — Service Worker é bloqueado por especificação em origem não seguras/opacas, `file://` é uma delas) e `caches.keys()` sempre retorna vazio pra este app. **Conclusão: sob `file://`, tecnicamente NÃO EXISTE cache de código/versão presa no sentido de PWA/Service Worker — isso nunca foi possível aqui.** (Seria possível se um dia o app for aberto hospedado, ex. Cloudflare — aí sim SW/Cache Storage existem de verdade; o app teve SW registrado via `vite-plugin-pwa` até ser removido em 30/08/2026, então um usuário que abriu uma build hospedada antes disso PODERIA ter esse problema — não é o caso do Rafael, que só usa `file://`.)

## Correção: popover "⋮" estourando pra fora da tela (05/09/2026)

Rafael reportou (testando o build da Etapa 4 acima): "janelas de submenus estourando pra fora da tela". Investigação (pedido explícito de "revise tudo e ajuste" — não é o gatilho da skill `revisao-ui-completa`, que exige relatório antes de aplicar; aqui o verbo do pedido é "ajustar", implementação direta):

**Inventário completo de `position: absolute` no projeto** (pra não corrigir só o caso que o Rafael viu e deixar outro igual): `.barra-meta > .marcador` (marcador dentro de uma barra de progresso, contido) — ok; `.item-lancamento-acao` (painel de ação ao arrastar a linha, mesma largura da própria linha) — ok; `.grade-icone-nome` (balão de nome do ícone no seletor, dentro de `.grade-icones` que já tem `overflow: auto` nos dois eixos — fica cortado/rolável dentro do modal, nunca "vaza" pra fora da tela) — ok, não é o mesmo tipo de bug; botão "×" de limpar busca em `BuscaEFiltros.tsx` (contido dentro do próprio campo de texto) — ok. **Só um caso realmente estourava:** `.menu-linha-popover` (o menu "⋮" de grupo/categoria em Categorias e Grupos, com "Restaurar ícone padrão"/"Inativar"/"Excluir").

**Causa raiz:** `.menu-linha-popover` é `position: absolute; right: 0`, ancorado no `.menu-linha-wrap` (`position: relative`) do próprio botão "⋮". Isso funciona quando sobra espaço à esquerda do wrap — mas numa linha de grupo/categoria que ocupa quase toda a largura da tela (medido: 390px de viewport), o wrap fica perto da borda esquerda, e um popover de 180px "crescendo pra esquerda" não cabe: a borda esquerda dele fica com X negativo (medido: -59px), ou seja, fora da área visível.

**Correção:** novo componente `src/components/MenuLinha.tsx`, substituindo as duas cópias quase idênticas que existiam em `Categorias.tsx` (uma pra linha de grupo, outra pra linha de categoria — mesmo HTML/CSS, duplicado). Usa `useLayoutEffect` + `getBoundingClientRect()` pra medir a posição real do popover depois de renderizado e, só quando ele ultrapassa a borda esquerda ou direita da tela (margem de 8px), aplica um `transform: translateX(...)` corretivo — `useLayoutEffect` roda antes do navegador pintar, então a correção já sai pronta no primeiro frame (sem flicker). Nenhuma classe CSS mudou; a correção é só um `transform` inline por cima de `.menu-linha-popover` quando necessário.

**Verificado antes de entregar:** `npx tsc --noEmit -p tsconfig.app.json` limpo; `npx oxlint` sem warning novo além de um esperado (`set-state-in-effect`, comentado no próprio arquivo — é o padrão medir-e-corrigir, não dá pra derivar durante o render porque depende do DOM já montado); build `file://` ok; Playwright confirmou **zero estouro** em 320px, 390px e 1280px de largura (testado nos primeiros 6 popovers da tela, grupo e categoria), zero erro de console, e regressão geral (N1 default, painel N0 abrindo/fechando, ground truth de Agosto/2026) inalterada.

## Etapa 7 (Ferramentas de teste — simular data de hoje) — reprocessamento de calendário (05/09/2026)

Roteiro de Parametrização Morfo, Etapa 7. Diferente das Etapas 4-6 (só o painel N0, a assinatura e o tour, todos aditivos sem risco real), esta etapa foi tratada como "grave/estrutural" (regra do próprio roteiro: "decidir o destino de uma ferramenta de teste ... só quando for gerada versão de Produção") e perguntada ao Rafael antes de construir — ele aprovou explicitamente, com uma exigência a mais: **"garantir que os processamentos de status vs data atual siga esse calendário — a cada mudança de data, deve reprocessar pagamentos e parcelas, recorrentes"**.

**Risco central, diferente do Kit original:** o Kit tinha um tenant "de teste" totalmente isolado do tenant real (barreira teste↔real) — simular data lá nunca tocava dado de cliente de verdade. O MFinp não tem esse ambiente separado: é o mesmo banco IndexedDB, os lançamentos reais do Rafael, sempre. Por isso a ferramenta foi desenhada com 3 salvaguardas: (a) nunca edita/apaga lançamento existente — só pode ADICIONAR ocorrência de série fixa que já deveria ter acontecido (mesma função `avancarSeriesFixasPendentes` de sempre, só lendo a data simulada); (b) só abre por dentro de Manutenção, nunca um botão flutuante sempre visível (mesmo padrão de acesso de Etapa 4/5/6); (c) um aviso permanente (`BannerDataSimulada`) fica visível em qualquer tela enquanto ativa, com botão de 1 toque pra voltar ao normal.

**O que foi construído:**
- `src/hojeSimulado.ts` (novo, raiz de `src/`, **não** em `kit/`) — `hojeEfetivoISO()` (leitura síncrona, cache em memória sincronizado via `liveQuery` do Dexie) e `useHojeSimuladoISO()` (hook). Fica na raiz — não em `kit/` — porque `recorrencia.ts`/`statusPagamento.ts`/`mes.ts` são módulos centrais do app que não devem depender do pacote de parametrização `kit/`; só a ação de "escrever + reprocessar" (`src/kit/SimularData.tsx`) depende de ambos os lados.
- Pontos que passaram a ler `hojeEfetivoISO()` em vez de `new Date()` direto: `statusPagamento.ts` (status Atrasado/A pagar/A receber), `recorrencia.ts` (`avancarSeriesFixasPendentes`), `mes.ts` (`mesAtualISO`, usado pela projeção "vai entrar/vai sair" de Resumo/Situação/Planejamento). **Fora do escopo, deliberadamente:** prefills de formulário (data padrão de um lançamento novo) e `mesInicial()` (que abre o app sempre na data REAL, nunca numa simulação esquecida de uma sessão anterior) — só o pedido explícito do Rafael (status/parcelas/recorrentes) entrou.
- `src/kit/SimularData.tsx` (novo) — tela "Ferramentas de teste" (campo de data + "Aplicar e reprocessar"/"Voltar pra hoje real", com mensagem "Reprocessado: N lançamento(s)...") e `BannerDataSimulada` (aviso permanente enquanto ativa). Acesso via Manutenção → "Ferramentas de teste" → "Simular data de hoje", fora do menu de engrenagem principal (mesmo padrão de Etapa 4/5/6).
- `Lancamentos.tsx`/`Carteira.tsx` ganharam uma chamada de `useHojeSimuladoISO()` só pelo efeito reativo (forçar re-render quando a data simulada muda) — as outras telas (Resumo/Situação/Planejamento) já se inscrevem em `db.configuracoes` via `useConfiguracaoIcones()` e reagem automaticamente.

**2 bugs reais encontrados e corrigidos na verificação (Playwright, não só tsc/oxlint/build):**
1. **Corrida de dados (race condition) no reprocessamento.** `aplicarNovaDataSimulada` salvava a nova data e chamava `avancarSeriesFixasPendentes()` em seguida — mas essa função lia `hojeEfetivoISO()`, cujo cache em memória só é atualizado de forma ASSÍNCRONA pelo `liveQuery` do Dexie (a escrita resolve antes do cache propagar o valor novo). Resultado: o primeiro reprocessamento depois de aplicar uma data sempre rodava contra a data ANTIGA, relatando "nenhum lançamento novo" mesmo com uma série claramente vencida. **Corrigido:** `avancarSeriesFixasPendentes(hojeISOForcado?)` ganhou um parâmetro opcional; `SimularData.tsx` passa a data recém-salva diretamente (nunca lida de volta via cache) nesse único ponto de chamada logo após escrever.
2. **Banner cobrindo o botão "‹ Voltar" (e a engrenagem) em toda tela.** A 1ª versão do `BannerDataSimulada` usava `position: fixed; top: 0`, pensado como "garantia" de ficar por cima de tudo — só que `.cabecalho-fixo` de cada tela também é `position: sticky; top: 0` dentro de `<main>` (único contêiner com rolagem do app), então o banner fixo cobria fisicamente o topo de qualquer tela, inclusive o botão de voltar (confirmado via `elementFromPoint`: o elemento sob o botão era o próprio banner, não o botão — cliques ali simplesmente paravam de funcionar enquanto a simulação estava ativa). **Corrigido:** removido `position: fixed` — como `#root` é `display:flex; flex-direction:column` e o banner é renderizado como irmão ANTES de `<main>` (`flex:1`), virar um bloco normal do fluxo já empurra `<main>` pra baixo sozinho, sem sobreposição nenhuma e sem precisar calcular altura/padding manualmente. Continua permanentemente visível (nunca some ao rolar) porque `<main>` é o único elemento com `overflow-y:auto` do app — o banner fica fora dele.

**Verificado antes de entregar:** `npx tsc --noEmit -p tsconfig.app.json` limpo; `npx oxlint` sem warning novo; build `file://` ok (`dist-local/index.html`, ~1.036 kB). Playwright cobriu: ground truth de Agosto/2026 e ausência do banner sem simulação ativa; criação de um lançamento fixo (mensal, dia 5) e de um lançamento único "a vencer" (+3 dias); aplicar uma data simulada ~40 dias à frente gerando corretamente 1 nova ocorrência da série fixa (mensagem "Reprocessado: 1 lançamento(s)..."); banner aparecendo em Ferramentas de teste E no app principal; status do lançamento "a vencer" virando Atrasado; "Voltar pra hoje real" fazendo o banner sumir (nos dois lugares) e o status voltar a A pagar/A receber; ground truth de Agosto/2026 inalterado ao final de toda a sequência; zero erro de console do início ao fim.

## Etapa 8 (Login real — trocando a entrada de verdade) (05/09/2026)

Roteiro de Parametrização Morfo, Etapa 8 (Site institucional deslogado/Login/Ambiente Logado). Tratada como "grave/estrutural" (a 2ª e última exceção da execução contínua desta rodada, junto da Etapa 7) e perguntada ao Rafael antes de construir: diferente de Etapas 4-7 (só telas alcançáveis por Manutenção, sem mudar o fluxo padrão), esta muda o PONTO DE ENTRADA real do app. Duas opções foram oferecidas — prévia isolada (Manutenção → "Ver Login", sem trocar nada de verdade) ou trocar a entrada de verdade — e o Rafael escolheu **"Trocar a entrada de verdade"**, mesmo sem plano/preço reais definidos (reaproveitando os placeholders da Etapa 5).

**Escopo, bem reduzido em relação ao `LoginView` do Kit original** (que é uma tela de site institucional completa: multi-página, planos, autocadastro, portal do cliente, convite de equipe): o MFinp é uso pessoal de uma pessoa só, sem backend (Decisão 6/Backlog #028) — nada de conteúdo de marketing real, múltiplos tenants ou convite de equipe existe pra portar. Construído: uma tela de entrada de verdade com formulário de "Criar acesso" (1ª vez, faz as vezes do autocadastro do Modelo Completo) ou "Entrar" (já existe credencial), mais um link enxuto "Ver planos" reaproveitando os placeholders da Etapa 5 — o mínimo de "site institucional deslogado" que faz sentido sem inventar conteúdo de marca que o Rafael nunca definiu.

**Autenticação é um portão de FLUXO/UX, não de segurança de dado** — documentado explicitamente em `db.ts`/`src/kit/auth.ts`: sem backend, não existe autenticação real possível num app 100% client-side (quem tem acesso ao arquivo/perfil do navegador já tem acesso ao IndexedDB inteiro, com ou sem "senha"). `credencialEmail`/`credencialSenha` são guardados em texto puro de propósito (criptografar não faria sentido nesse contexto).

**O que foi construído:**
- `src/kit/auth.ts` (novo) — `criarAcesso(email, senha)`, `entrar(email, senha): Promise<boolean>`, `sair()`, `redefinirAcesso()` ("esqueci minha senha" — como não existe backend/recuperação real, a única saída honesta é permitir cadastrar credencial nova; nunca toca em lançamentos/categorias/contas/grupos/ícones, só nos 2 campos de credencial e na sessão — existe pra nunca deixar o Rafael genuinamente trancado pra fora do próprio app).
- `src/kit/LoginView.tsx` (novo) — tela de entrada, com os dois modos (criar/entrar), validação (e-mail preenchido, senha ≥ 4 caracteres, confirmação bate), modal "Ver planos" (reaproveita `PLANOS_STUB`) e modal "Redefinir acesso".
- `db.ts` — `ConfiguracaoIcones` ganhou `credencialEmail?`/`credencialSenha?`/`sessaoAtiva?` (mesmo padrão aditivo de sempre, sem bump de schema).
- `src/kit/AppRoot.tsx` — agora lê `sessaoAtiva` via `useLiveQuery` e SEMPRE renderiza `<LoginView/>` primeiro quando não há sessão ativa — o app não abre mais direto em N1. Uma vez logado, a sessão persiste entre aberturas do app (`sessaoAtiva` gravado no Dexie) — sem isso, o Rafael precisaria logar de novo toda vez que abrisse o arquivo, inviabilizando o uso diário.
- **"Minha Assinatura" promovida pro menu de engrenagem principal** (`ROTULO_CONFIG`, `App.tsx`) — desde a Etapa 5 ficava de propósito fora dali, com a nota "o lugar definitivo disso é o Ambiente Logado da Etapa 8"; com a Etapa 8 construída, essa promessa foi cumprida e o acesso provisório via Manutenção foi removido.
- `Manutencao.tsx` ganhou uma seção "Conta" com botão "Sair" (zera só `sessaoAtiva`, nunca dado financeiro).
- **Bônus, corrigido antes de construir a Etapa 8 (achado ao revisar `configuracaoIcones.ts` antes de adicionar mais campos ao mesmo singleton):** `salvarConfiguracaoIcones()` montava o `.put()` listando só os 4 campos "de ícone" + `...patch`, sem nunca espalhar `...atual` por completo — como `Dexie.put()` substitui o registro inteiro (não faz merge), toda chamada que não citasse um campo aditivo de outra etapa (`ordemAbas`, `planoId`, `hojeSimuladoISO`) o apagava silenciosamente. Corrigido espalhando `...atual` primeiro. Ver detalhe completo no comentário da função.

**Bug real, grave, encontrado e corrigido na verificação (Playwright):** a 1ª versão de `LoginView.tsx` tinha `if (config === undefined) return null` pra evitar mostrar "Criar acesso" por um instante antes de saber se já existia credencial — só que `useLiveQuery` retorna `undefined` tanto "ainda carregando" quanto "carregou e não existe registro nenhum" (o caso NORMAL de um app nunca logado antes, exatamente quando esta tela precisa aparecer). Sem distinguir os dois casos, um banco genuinamente vazio (ou seja, TODO mundo na primeira vez que abrisse esta build, incluindo o próprio Rafael) deixava essa condição `true` PRA SEMPRE — a tela nunca renderizava nada, `#root` ficava vazio, app inteiro travado numa página em branco, sem nenhum erro de console (silencioso). Corrigido com o mesmo sentinela `CARREGANDO` (`Symbol`) já usado em `AppRoot.tsx`, passado como 3º argumento de `useLiveQuery` — só ele distingue "carregando" de "vazio de verdade".

**Verificado antes de entregar:** `npx tsc --noEmit -p tsconfig.app.json` limpo; `npx oxlint` sem warning novo; build `file://` ok (`dist-local/index.html`, ~1.043 kB). ### Correção pós-entrega (05/09/2026, mesmo dia): 2 bugs reais achados pelo próprio Rafael usando a Etapa 8 de verdade

Rafael reportou, usando a build entregue: (1) "Ainda tem telas fora escondendo parte, exemplo Plano" e (2) "preciso saber que senha e login entrar, pois não consigo logar ou tem problema". Investigação (reproduzindo a ação mais provável, não supondo) confirmou 2 bugs reais em `LoginView.tsx`, nenhum dos dois pego pela verificação da entrega original (que só testou e-mails já válidos, tipo `nome@dominio.com`, e só viewports "normais"):

1. **`type="email"` bloqueava o próprio submit em silêncio.** O campo de e-mail usava `<input type="email">` — sem `required`, mas isso já basta pro NAVEGADOR validar o formato no submit e travar o `onSubmit` (nosso `salvar()`) de rodar quando o texto não tem "@", sem nenhum aviso visível nesta tela (o balão nativo do Chrome passa despercebido ou nem aparece, a depender do navegador/SO). Ou seja: se o Rafael digitasse qualquer coisa sem "@" (bem provável — ele não sabia que precisava ser um e-mail "de verdade", já que nada na tela avisava isso antes de tentar), clicar em "Criar acesso e entrar"/"Entrar" literalmente não fazia nada, nenhum erro, nenhuma reação. **Mesma classe de bug já documentada neste arquivo pro formulário de Transferência** (`required` nativo bloqueando submit em silêncio) — reforça que esse padrão (nunca depender de validação nativa do HTML pra feedback visível; sempre validar em JS com mensagem própria) precisa ser checado em TODO formulário novo, não só copiado de exemplos antigos. Corrigido: `type="text"` + `inputMode="email"` (mantém teclado de e-mail no celular) + validação de "@" feita à mão em `salvar()`, sempre com `setErro(...)` visível.
2. **Centralização "insegura" de flexbox escondia o topo da tela em viewport curto.** O wrapper externo da tela de Login usava `justifyContent: 'center'` pra centralizar o cartão verticalmente. Com conteúdo mais alto que a viewport (telclado do celular aberto — bem provável, já que é exatamente durante o ato de digitar e-mail/senha — ou janela pouco alta), isso empurra o TOPO do conteúdo pra Y NEGATIVO, e não existe como rolar "antes do topo da página" pra alcançar — confirmado via Playwright: título em `y=-88px` numa viewport de 300px de altura, `window.scrollY` preso em `0` mesmo tentando rolar pra cima. Na prática, o título "MorfoFinP" e possivelmente o próprio campo de e-mail ficavam permanentemente inacessíveis. Provavelmente a causa raiz do "telas fora escondendo parte" relatado (o mesmo padrão pode se repetir em qualquer tela nova que centralize verticalmente por flex sem cuidado — vale checar em telas futuras). Corrigido com o padrão de **"centralização segura"**: o wrapper externo não centraliza mais nada (fica no topo do fluxo normal, sempre alcançável rolando de cima pra baixo); quem centraliza é o cartão interno, via `margin: 'auto 0'` — margem automática ocupa o espaço sobrando quando existe, mas nunca fica negativa quando não sobra espaço, então o cartão simplesmente começa do topo quando a viewport é curta.

**Resposta direta à pergunta do Rafael ("que senha e login entrar"):** não existe credencial pré-definida nenhuma. Na primeira vez que esta build roda (banco sem `credencialEmail`/`credencialSenha`), a tela sempre abre em modo "Criar acesso" — o Rafael escolhe QUALQUER e-mail (só precisa ter "@", não precisa ser um e-mail real que funcione) e QUALQUER senha (mínimo 4 caracteres) que ele mesmo queira usar dali em diante. Essa escolha fica salva no navegador (Dexie/IndexedDB) e vira o login permanente desse perfil de navegador — é o autocadastro do Modelo Completo, não uma conta pré-existente em algum lugar.

**Verificado após a correção:** `npx tsc --noEmit -p tsconfig.app.json` limpo; `npx oxlint` sem warning novo; build `file://` ok. Playwright (script novo, descartado após rodar — nunca committar script de teste ad hoc): e-mail sem "@" agora mostra o erro visível "Digite um e-mail válido (com @)." em vez de travar em silêncio; viewport 390×300 (simulando teclado aberto) com o título do topo em `y >= 0`, alcançável por scroll normal; fluxo completo (criar acesso → entra no app → reload preserva sessão → sair → entrar com senha errada mostra erro → entrar com senha certa entra) sem nenhum erro de console; regressão do popover de engrenagem ("Minha Assinatura" visível), Ferramentas de teste (banner não cobrindo "‹ Voltar") e ground truth de Agosto/2026 todos intactos.
